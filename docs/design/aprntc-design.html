1The concept

The #1 limitation of production LLM agents is that they don’t learn from experience — they stay stateless and need manual prompt/dataset work to improve. aprntc closes that gap with an autonomous observe → label → distill → evaluate → promote loop, with a human only at the promotion gate.

An apprentice (“child”) agent is cloned from a live parent, passively shadows it, distills lessons from what worked and what didn’t, becomes measurably better, and — once a human approves — is promoted to replace it. Then the cycle repeats.

Scoping principle (load-bearing)
aprntc is not a monitoring/observability product. It learns from the parent’s overall response quality to produce a better successor — episode/task-level quality signal is the target, not exhaustive trace capture.

2What the “child” actually is

The single most important thing to understand: there is no separate “child program.” An agent = a fixed engine (the LLM, retrieval, tools, the loop) + a Playbook (a config artifact: system prompt + directives + exemplars + “watch-out” lessons). Parent and child share the exact same engine — the only difference between them is the Playbook.

Figure 1 — The parent and child share one engine. Only the Playbook differs; promotion swaps it.

This is the Phase-1 mechanism: playbook distillation, not fine-tuning. The consequences map directly to real-world constraints:

  • Works on closed-source LLMs. You can’t fine-tune Seed-2.0 / DeepSeek — but you can change how they’re prompted and what examples/lessons they’re given.
  • Attributable. Every lesson traces back to the trajectories that produced it.
  • Reversible. A bad promotion is one config swap to undo — no opaque weight changes.

4Production integration

aprntc sits beside your agent, never in front of it. The production agent keeps running exactly as today; aprntc is a separate service that observes, improves, and proposes. It is never in the user request path — if it’s down or wrong, production is unaffected.

Figure 3 — aprntc observes via a read-only tap (inbound) and serves the improved playbook the agent pulls (outbound). The gated config swap is the only write back to production.

Connecting an external agent (e.g. a LangChain agent)

aprntc owns neither the agent’s code nor its prompt, so the Playbook becomes a contract with two halves:

Inbound (observe) — built
The agent’s traffic flows into aprntc via a tap (egress proxy / OTel / MCP). Read-only. This is how aprntc sees behavior without owning the code.
Outbound (control) — built
The agent pulls its active playbook from aprntc’s config-fetch API (GET /api/playbooks/{id}/active). Promotion updates what’s served; the agent picks it up. Rollback serves the prior version. No redeploy.

Initial G0 = the customer registers their current system prompt (aprntc needs only the prompt text, not the code); if they don’t, aprntc infers an approximate G0 from the system prompt the tap observed.

6Quality & the acceptance bar

Quality is anchored on outcomes. Reliability order: outcome > explicit user feedback > implicit > LLM judge (the judge is a prior, never the authority). Fusion weights are learned from how well each source historically agreed with the anchor — a judge that disagrees with real outcomes/feedback is automatically down-weighted.

A distilled child is promotable only when all hold on a frozen held-out set the distiller never saw:

Honest finding
A playbook makes the agent reliably apply lessons — it can’t teach the base model capabilities it lacks. The apprentice only measurably wins where the parent genuinely fails or is inconsistent and there’s ground truth to steer toward. On a real BytePlus support agent with honest headroom (a thin parent), the distilled child won 65–85% of comparisons.

0004Tap = protocol-boundary collectors, wrapping OSS
0005aprntc is a learning product, not observability (best-effort capture)
0006Outcome-anchored quality + playbook distillation (no fine-tuning in Phase 1)
0007Canonical Trajectory schema
0008Tap build order: core + SDK wrapper first
Hard-won lesson
An SDK-equivalence (“oracle”) test only proves we match the SDK given the same inputs — it can’t catch a wrong input. The VikingDB signer matched the SDK byte-for-byte yet still 403’d live, because both used service="air" when the V2 API needs service="vikingdb". The live API is the ultimate oracle — which is why every stage is verified against live infra, not just unit tests.

8Status & what’s built

The planned roadmap is complete: the MVP loop, the v1 feature set, and productionization.

  • MVP loop — signing gate, trajectory schema/store, AgentTap, eval/labeling, VikingDB memory, distillation + child, promotion gate + lineage. Live-verified on BytePlus.
  • v1 features — distillation quality, real BytePlus support agent, external collectors (proxy/OTel/MCP), online shadow + canary, learned fusion weights, auto-promotion, multi-agent fleets. (Fine-tuning parked — open-weight models only.)
  • Productization — playbook registry + config-fetch API, Docker deploy, API-key tenancy, ops (scheduler/retry/metrics), Google sign-in.
